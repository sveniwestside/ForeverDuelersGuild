Source review identifies a reproducible boundary: native grouped/count flags can be present while QueueWow's required full party1 identity is unavailable. The actual-TOC regression reproduces this outcome with one-sided native identity delay and rejected early PARTY controls. 0.5.7 separates PENDING from a positive CHANGED group, waits within existing deadlines and rechecks exact membership before planning/travel/leave. A wrong native GUID/name, third member or raid still cancels. Authenticated callbacks also enforce the original 60-/20-second group/plan bounds before the next tick; a pending PLAN_ACK or GO cannot commit/reset travel time or acknowledge start.

Release validation passes 48 compiled files / 23 Lua suites / 8,108 assertions and 48 Python tests. The recovered actual-TOC flow uses native-tested Tirisfal metadata, continent 0 and normalized shared coordinates, drops grouped WHISPER, then completes matching READY, both explicit rated choices, native countdown/result and reciprocal ratings. Other cases cover cancellation before first group Tick, late exact proof during cleanup, missing/restricted/error native getters, invalid groups and packet arrival at the deadline. Native group API calls and exact identity requirements are retained; classification adds no alternate native position/phase evidence. Independent review found no new ownership, consent or rating bypass. Paired in-game 0.5.7 queue completion remains pending.

Treat unrecognized rendered grammar as missing result evidence and test these locales explicitly before claiming support. Inspected English, German, French, Spanish, and Simplified Chinese templates use ordinary integer/string placeholders, but still require live name/message verification.

`CHAT_MSG_SYSTEM` exists and its first argument is `text`. `UI_INFO_MESSAGE` and `UI_ERROR_MESSAGE` exist with `(errorType, message)`. Sources: [ChatInfoDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua), [SystemDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_APIDocumentationGenerated/SystemDocumentation.lua).

**REQUIRES LIVE CLIENT VERIFICATION:** native C++ decides which event carries each localized countdown/result/request/cancellation message; the extracted Lua does not prove that delivery mapping, timing, or ordering. Observe this on both clients using debug/event tracing. The conservative integration can infer a start from a locally observed localized countdown after rated agreement, then wait out the remaining seconds. That is an inferred timestamp, not a documented duel-start event. Missing or secret countdown/result evidence must leave the duel unrated. A result should require local finish evidence and matching local names, with a bounded grace period for either arrival order; opponent reports alone are not local native result evidence.

## Native popup integration

The current native handler is in [Blizzard_Game/Shared/EventImplementation.lua](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_Game/Shared/EventImplementation.lua#L215): `DUEL_REQUESTED` shows `StaticPopup_Show("DUEL_REQUESTED", playerName)`. The [Retail finish handler](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_Game/Mainline/EventImplementation.lua#L428) hides the request and boundary popups.

The native definition has accept/cancel callbacks, timeout, and Escape handling. It does not cancel from `OnHide`. In the inspected [StaticPopup.lua](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_StaticPopup/StaticPopup.lua#L410), `StaticPopup_Hide` hides matching dialogs and handles `OnHide`; it does **not** invoke the cancel callback. Therefore hiding the request can suppress presentation without intentionally declining it in this source baseline.

Use an addon-owned frame. Defer native suppression using `C_Timer.After(0, callback)` and recheck request generation/state in the callback so late work cannot hide a newer request. Build/show a functioning replacement before hiding the native dialog. Do not overwrite `StaticPopupDialogs.DUEL_REQUESTED`, unregister Blizzard events, replace global functions, or hook private dispatch internals. Timer API: [UITimerDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_APIDocumentationGenerated/UITimerDocumentation.lua).

**REQUIRES LIVE CLIENT VERIFICATION:** native and addon event-handler ordering; deferred hide/re-show behavior; Escape and request expiry; interaction with other duel UI addons; taint logs; accept/decline in and out of combat. Legacy `AcceptDuel`/`CancelDuel` have native UI call-site evidence but no generated protection metadata here. Native usage in a button callback does not prove a message-handler call is permitted in every context. `pcall` can catch an error; it does not make protected actions legal or prove the server accepted an action. If acceptance fails, invalidate rated negotiation and preserve/restore a usable native unrated path. An explicit click after agreement is a possible fallback if the live client requires it.

## Addon communication

Verified in [ChatInfoDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua) and [ChatConstantsDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/4e3cbb8c5609e4bfc332c0aebbfa4d79731fab59/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatConstantsDocumentation.lua):

- `C_ChatInfo.RegisterAddonMessagePrefix(prefix)` returns `Enum.RegisterAddonMessagePrefixResult`, **not a boolean**. `Success` is 0; `DuplicatePrefix` is 1; invalid/max-prefix results are failures.
- `C_ChatInfo.SendAddonMessage(prefix, message, chatType, target)` returns `Enum.SendAddonMessageResult`. `Success` is 0. Throttling and routing failures are explicit enum values. Lua truthiness is not a success test because numeric failures are also truthy.
- `CHAT_MSG_ADDON` begins `(prefix, text, channel, sender, target, ...)`. Filter prefix, channel, normalized sender, version, session, and identity before mutating state.
- The send API disallows secret arguments. Send success is local submission, not an acknowledgment or evidence of remote delivery.

**REQUIRES LIVE CLIENT VERIFICATION:** `WHISPER` reachability on Forever, cross-realm/cross-faction delivery, target-name normalization, throttle behavior, packet/event ordering, and whether interference from other installed addons can alter availability. Compact bounded payloads, bounded retries/timeouts, and safe unrated degradation remain required. Do not claim atomic agreement or guaranteed complementary persistence over a lossy transport.
